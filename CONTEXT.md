# Conversation context and persistence

lowlight owns prompt assembly and conversation storage. The endpoint receives ordinary OpenAI-compatible chat requests. Context management does not require tool calling or MCP.

## Three kinds of conversation state

The **system instructions** combine the user's base prompt with explicitly selected skill bodies. They are rebuilt from canonical values for each request and survive compaction unchanged. The base prompt and each skill snapshot are saved separately, so changing instructions does not accumulate repeated copies.

The **active model context** contains completed user/assistant turns, an optional checkpoint summary, and the cumulative number of turns removed from the verbatim context. Summaries are presented as conversation notes rather than promoted into system instructions. Failed, stopped, and local-notice messages are excluded.

The **display transcript** retains all visible messages, including partial responses and notices. Removing a turn from active context never deletes it from the transcript. Saving and resuming preserves both representations; it does not reconstruct model context from potentially incomplete display messages.

## Budgeting

The input budget is:

```text
min(window × compactAtPercent / 100,
    window - maximumOutput - safetyReserve)
```

The application defaults are a 32,768-token window, 512 output tokens, 1,024 safety tokens, and a 90% threshold. Invalid reserves are rejected. The model window is configured explicitly because standard model metadata does not provide a reliable context limit.

Before sending, the client includes the pinned instructions and current user prompt, then budgets complete history turns. A prompt that cannot fit alongside the instructions is rejected. Input counts use an approximate serialized UTF-8 byte estimate divided by four, including message overhead; the UI marks them with `≈`.

`/context` reports the estimate, budget, model window, reserves, retained turns, cumulative omissions, and checkpoint presence. `/usage` separately reports exact token counts when the endpoint supplies them through standard streaming usage events. Usage counters are runtime state and restart on resume or reconnect.

## Checkpoint compaction

`checkpoint` is the application's default strategy. Before a chat request that would exceed the input budget, the client asks the selected model to summarize older completed turns, preserving a recent complete tail when space permits. Existing notes are incorporated into the next checkpoint. `/compact [GUIDANCE]` runs the same process explicitly; optional guidance can ask it to preserve particular decisions or details.

Compaction is an ordinary model request and consumes input and output tokens. Larger histories may require bounded batches, with at most eight summary requests per operation. Each request must fit the configured budget. Summary responses must complete normally and fit the retained context; truncated or failed summaries are rejected.

Automatic compaction is transactional: the proposed checkpoint and following assistant turn become active only after that response succeeds. If summarization, generation, or cancellation interrupts the operation, the previous context remains intact. Manual `/compact` commits when its summary operation succeeds. The transcript remains unchanged apart from local status notices.

Checkpoint notes are generated by the model and may lose or misstate details. The saved transcript remains the original record. Compaction cannot make an arbitrarily large pinned prompt or a single oversized turn fit; the client reports the budget error when it cannot construct a valid request.

## Sliding window

`--context-strategy slidingWindow` disables automatic model summarization. The client selects the newest contiguous complete turns that fit and omits older turns only when a response succeeds. It retains the current prompt and canonical instructions. This mode avoids automatic compaction requests, while omitted details are no longer sent to the model. Explicit `/compact` remains available.

## Durable sessions

Version 1 JSON snapshots are stored under `~/.lowlight/sessions/chat`, or the directory selected by `--sessions-directory`. Each filename is a UUID. `/sessions` lists valid records with their workspace; `/resume` accepts a UUID, unique prefix, or `last`. The default library also reads the previous `~/.midnight/sessions/chat` and Application Support locations, writing subsequent saves to the new home.

Snapshots include identity and timestamps, title, model and endpoint, workspace, token policy, base system prompt, active skill snapshots, active context, transcript, and input history. Authentication tokens and usage counters are not stored. Resume restores the saved chat settings and instructions; authentication comes from the current process environment.

Writes are validated and atomic. Autosave runs before and after generation, every ten seconds during streaming, and before switching conversations or exiting. `/save [TITLE]` saves immediately. An abrupt process termination may lose changes since the last successful checkpoint. Saving failures are visible, and an existing invalid or unsupported file is never silently overwritten.

On load, any transcript response still marked streaming becomes stopped. Its partial text remains visible but is not inserted into completed model context. Corrupt, mismatched, linked, or unsupported records are skipped by listings and `last`, with diagnostics available through `/sessions`.

`/new` and `/clear` save the old chat before starting fresh context and transcript, retaining the base prompt and selected skills. Model, endpoint, and context-window changes preserve conversation state. Prompt edits and skill changes apply to the next request without rewriting previous messages or checkpoint notes.

## Local instructions

`/system` edits the canonical base prompt. `/skill` opens a local picker, `/skill list` displays metadata, and `/skill use NAME` explicitly snapshots a selected file's instruction body. `/skill create NAME` opens an editor for a new `.midnight/skills/NAME/SKILL.md` in the workspace. Only active skill bodies enter model context; the available catalog is not sent. Resumed chats use their saved snapshots until the user reloads a skill.

Workspace selection controls local skill discovery and is persisted with the chat. It does not execute workspace code. Tool calling, MCP, executable skill helpers, Ruby interpreters, and harness execution are outside the current implementation.
